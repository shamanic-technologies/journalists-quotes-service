# journalists-quotes-service CLAUDE.md

Backend that ingests journalist quote requests (HARO emails + Featured.com Premium API), clusters them into Gold opportunities, and surfaces the next-best per brand-set tuple.

## Data layering (B/S/G)

| Layer | Table | Role |
|-------|-------|------|
| **Bronze** | `provider_quote_requests` | Raw silver-row of each source artifact. Append-only via `onConflictDoNothing(provider, ingestion_channel, external_id)`. `raw jsonb` captures the full upstream payload. |
| **Bronze** | `inbound_emails` | Raw Postmark webhook payload, `raw_payload jsonb`. Idempotent on `message_id`. Drained by `/internal/process-inbound-emails`. |
| **Silver** | `quote_opportunities` | Canonical Gold cluster keyed by `fingerprint(text, outlet)` — one row per de-duplicated opportunity. Built lazily by `attachOrCreateCluster` at ingestion time. The repo informally calls this the "Gold cluster" id because external IDs we return reference this table. Doctrinally still silver: it's the canonical entity, not a business projection. |
| **Gold** | `quote_priorities` | Scored projection. Natural key: `(quote_opportunity_id, brand_ids[])` — one row per `(opportunity, brandSet tuple)`. Materialized as a table (not a view) because scoring is expensive. Idempotent upsert. |
| **Gold** | `quote_pitches` | Submitted/drafted/error pitch record. Natural key: `(quote_opportunity_id, brand_ids[])` exact-match for the non-blocking statuses (partial unique index, see `schema.ts`). |

### Exhaustion-driven trigger (no cron, no time-based TTL)

`/orgs/opportunities/next` is the only refresh path. Each call:
1. `selectUnscoredBatch` — picks at most **10** Gold clusters with NO row in `quote_priorities` for the exact `brand_ids[]` tuple. Anti-join via `LEFT JOIN ... IS NULL`. Filters expired `canonical_deadline`. **Only SUBMITTABLE clusters** (one EXISTS predicate `submittableSilverExists`: a silver row with `featured_question_id IS NOT NULL` OR `pitch_email IS NOT NULL`) — discovery leads are never scored/served. Ordered by `first_seen_at ASC` for determinism.
2. **If batch empty** → `ingestPremiumQuestionsToSilver`: pull Featured **premium questions** from **expert-quotes-requests-service** (EQRS) via `GET /orgs/featured/premium-questions`, project into silver + Gold cluster. **MVP = premium only** — premium questions are the only Featured feed that is programmatically submittable (they carry `featured_question_id`; the discovery `/opportunities` feed is null on that field and is NOT ingested). Premium is a pass-through with **no cursor** (`eqrs_sync_state` untouched) — pull the full list each exhaustion tick; idempotent upsert keys on synthesized `external_id = "featured-premium-<fqid>"`. The discovery `ingestFeaturedToSilver` path is dormant (removal = follow-up).
3. `scoreUnscored` — **LLM relevance judge** (not RAG). Fetches the brand-set profile from `brand-service POST /orgs/brands/extract-fields` (cached 30d), then **one** `chat-service POST /complete` call (`google/flash`, temp 0.2, strict `responseSchema`) returning a **0-100** relevance score + reasoning per opportunity. Collective score for the brand-set tuple, stored one row per `(opportunity, brand_ids[])`. Score keying = tuple; serve/dedup keying = atomic per brand (see global "collective scoring, atomic exclusion").
4. `selectBestNonPitched` — SELECT MAX(score) above `SCORE_THRESHOLD` (default **10**, 0-100 scale), filtering `quote_pitches` blocking rows for the brand-set under **ANY campaign** (atomic per-brand exclusion — **never** campaign-scoped; a brand cannot answer the same Featured question twice) AND `submittableSilverExists`. Tie-break: `first_seen_at ASC` (oldest cluster wins). Bands derived at read: ≥70 direct / ≥30 adjacent / <30 off-topic. **`SCORE_THRESHOLD` (the /next auto-submit floor) is DECOUPLED from the semantic bands: the floor is 10, NOT the 30 "adjacent" band boundary.** /next auto-pitches everything ≥10 (incl. weak 10-29), only pure noise <10 is dropped. The floor gates /next auto-submit ONLY — reads (`GET /orgs/opportunities`) have NO floor.

**Submittability contract.** `/next` + `/ranked` payloads carry `submittable: boolean` + `deliveryMethod` (`featured_api` | `email_reply` | `external_manual`), computed per representative via `computeDelivery`. `/reply` routes by the same function: `featured_api` → EQRS `submitAnswer`, `email_reply` → email-gateway, non-submittable (discovery lead, no fqid, no email) → **422** `{status:"not_submittable", deliveryMethod:"external_manual", reason, pitchUrl}` — never a raw 400. Catalog (next/ranked/stats-eligible) is filtered to submittable clusters, so discovery leads are excluded from what operators can act on.

EQRS is pulled ONLY when the consumer has fully drained the silver pool for the brand-set tuple. Natural backpressure: high-throughput callers consume what landed in silver before triggering an upstream pull. No wall-clock TTL on JQS side — EQRS owns the per-org Featured.com refresh policy.

**Invariants:**
- Bronze immutable (no UPDATE; only INSERT … ON CONFLICT DO NOTHING).
- Silver/Gold rebuildable from bronze (`fingerprint` is deterministic; truncating `quote_priorities` → next `/next` re-scores).
- No score row keyed by `orgId` — `quote_priorities` is by `(opportunityId, brand_ids[])` tuple, shared across orgs that use the same brandSet. Org isolation enforced via silver-pool EXISTS check.
- **Every bulk DB op over an EQRS-sized list MUST go through `chunkRows` (`src/lib/db-chunk.ts`).** The premium feed is a full-list pass-through with NO cursor, so batch size = catalog size and grows ~500/week unbounded. Postgres caps a single statement at **65,534 bind params** (one per column per row): the 13-column silver upsert in `opportunity-pipeline.ts` therefore dies at **5,042 rows**, the 5-column Gold-cluster upsert at 13,107, and `inArray(fingerprints)` at 65,535. Prod incident 2026-07-29 (#107) — the catalog hit 5,100 and EVERY `/orgs/opportunities/next` + `/discover` 500'd with `MAX_PARAMETERS_EXCEEDED`, failing campaign runs every 60s. Diagnose as a **statement-width** failure, not a slow query and not a connection-level failure (the historical Neon-suspend cold-start class is gone — the DB is a single always-on Postgres container now): the stack bottoms out in `postgres/src/connection.js toBuffer`, and the tell is a bulk `.values(bigArray)` whose length tracks an upstream catalog. Chunking is write-safe because every bulk op is `ON CONFLICT` idempotent and dedupe runs across the WHOLE batch before splitting (so no chunk can hit errcode 21000). Regression coverage: `tests/integration/premium-ingest-oversized.test.ts` (6,000 rows) + `tests/unit/db-chunk.test.ts`.

**Why no cron, no TTL:**
- Single replica — one instance of this service runs, no horizontal scale-out.
- Trigger frequency = campaign tick (~1/min per active campaign), bounded.
- Featured fetch (~500ms) absorbed into the /next budget only when the pool is exhausted; chat-service call (~1-2s for 10 docs × M brands) dominates anyway.
- Time-based TTL caps how fresh Featured opps can land in the catalog (5min stale-window). Exhaustion-driven trigger has zero stale-window — new opps surface on the next call after they're scored.

If we ever scale-out to multiple replicas, in-process state for "has this org been ingested yet" becomes per-replica and inconsistent. Mitigation: idempotent upsert means the worst case is N replicas each calling Featured `listOpportunities` once per pool-drain (multiplicative on Featured rate budget). At that point introduce a DB-backed lock (`SELECT … FOR UPDATE SKIP LOCKED` on a `featured_sync_state` row) so only one replica refetches per exhaustion event.

## Routes

- `POST /orgs/opportunities/next` — score-as-you-go write+read (above). **Identity is header-only — `x-brand-id`, `x-user-id`, `x-run-id`, `x-campaign-id` are ALL mandatory (400 if any missing); no request body.** `x-campaign-id` stamps new pitches (`quote_pitches.campaign_id`) + scopes run-tracking; it does **NOT** scope pitch exclusion — the block is **atomic per-brand under ANY campaign** (matches `/reply`'s brand-scoped idempotency). A campaign-scoped block deadlocks: `/next` would re-serve an opp `/reply` then refuses as `already_submitted` (prod incident, brand `f4d73dab`: every campaign stuck re-serving the same score-100 opp already pitched under a NULL campaign). Powers Feature 1 (auto-reply workflow loops `/next` → reply → repeat).
- `POST /orgs/opportunities/discover` — **write-only batch scorer** (Feature 2 catalog fill). Scores ≤10 unscored submittable clusters for the brand-set ordered by **deadline ASC NULLS LAST** (urgency-first, the cheap pre-score priority proxy), pulling Featured premium from EQRS on local exhaustion. Returns `{ scored, exhausted, brandIds }` — NO opportunity payload. `exhausted: true` ONLY when, after an EQRS-premium ingest attempt, nothing remains to score (`scored: 0`). **Credit gate lives in the caller's workflow, NOT JQS** — each call = exactly one judge call (bounded cost), so the caller loops `while (!exhausted)` (budget-checking between calls) to drain the pool; overshoots a budget by at most one batch. Same mandatory headers as `/next`. Thin sibling of `pickNextOpportunity` (shares `selectUnscoredBatch`/`ingestPremiumQuestionsToSilver`/`scoreUnscored`), minus the best-1 selection + read.
- `GET /orgs/opportunities` — **canonical pure-read** paginated list (the renamed read surface). SELECT-only over `quote_priorities ⋈ quote_opportunities`, filters expired deadlines + restricts to submittable (premium) clusters, annotates latest `pitchStatus` (**brand-atomic — any campaign's pitch counts**, regardless of the `?campaignId=` query). **NO relevance floor** (v0.13.x): returns EVERY scored premium opp with its `score` so the dashboard filters by relevance client-side — `SCORE_THRESHOLD` gates ONLY `/next` auto-submit, never the reads. Never scores. Query: `?campaignId=&limit=&offset=` (campaignId optional; does not affect pitchStatus scope). Polled by the HITL dashboard (~5s) for **both** features.
- `GET /orgs/opportunities/stats` — brand-set scoped catalog metrics (silverPoolSize, scoredCount, eligibleCount, pitchedBlocking, expiredCount, bestEligibleScore). Pure read. `eligibleCount`/`bestEligibleScore` carry **no relevance floor** — "eligible" = scored + non-expired + submittable + not pitch-blocked (any score). Pitch-block is **atomic per-brand under ANY campaign** — the `?campaign_id=` query is accepted (logged) but does **NOT** scope `pitchedBlocking`/`eligibleCount`.
- `POST /orgs/opportunities/:id/reply` — submit pitch. `:id` = Gold cluster id. Idempotent on `(quote_opportunity_id, brand_ids[])` — **brand-atomic, NOT campaign-scoped** (a brand cannot answer the same Featured question twice). **Diagnostic gotcha: `opportunity-reply.ts` emits NO `console.log` — absence of `/reply` lines in the deployed service's container logs does NOT mean `/reply` was never called. Source of truth for "was a pitch submitted" is the `quote_pitches` table, not the logs.** Reads `campaignId` from the request **body** (not `x-campaign-id` header) — a caller that omits it stamps `campaign_id=NULL` (harmless post-atomic-exclusion fix, but attribution is lost; header-source is a follow-up). **Dead-question terminal exclusion (prod question 83147):** a Featured submit that fails with `404 Question not found` (EQRS surfaces it as a 200 error result OR an `EqrsServiceError` — matched by `isDeadQuestionError` = `/question not found/i`) writes a pitch with the terminal status **`question_not_found`** and returns **410 Gone**. Unlike the retryable `error` status, `question_not_found` is **BLOCKING** — it participates in the partial unique index (deliberately NOT in the index's exclusion list) and in `BLOCK_STATUSES`, so `selectBestNonPitched`/`/next` never re-serve the dead question for that brand-set again (stops the infinite 404 re-fail loop). A generic/transient submit error stays `error` (re-servable). The dead insert uses `onConflictDoNothing`; a second `/reply` short-circuits on the idempotency check and returns 410 without re-hitting Featured.
- `POST /orgs/quote-pitches/reconcile-outcomes` — **publication-outcome reconcile** (Featured/Connectively). Pulls TWO Connectively feeds (both EQRS paginated pass-throughs, in parallel) and matches each onto a pitch by **`(featured_question_id, featured_profile_id)`**:
  - `GET /orgs/featured/submissions` (Connectively `/submitted`) → advances `status` **forward-only** `submitted → selected / published / not_selected` (`In Review` stays `submitted`), and records `publication_source` (outlet name), `outlet_domain_rating` (DR), `backlink_attribution` (verbatim "DoFollow"/"Unlinked"/"Unknown"), `outcome_observed_at` (OUR observation time).
  - `GET /orgs/featured/published` (Connectively `/published`) → records the **published article placement fields**: `featured_article_url` (Connectively `publishedLink`, the real article URL), `article_title` (`articleTitle`), `published_at` (`publishDate`, when the article went live). These NEVER clobber an existing non-null value with null (no data loss). **This is the feed that carries the article link the press report links out to — the `/submitted` feed does NOT expose it, which is why the report's Article column was blank before #102.**
  Idempotent (a re-run with unchanged upstream data writes nothing). Fail-loud: an EQRS error → 502. The advanced statuses are already in `BLOCK_STATUSES` + the partial-unique-index, so advancing keeps the pitch blocking (a brand still can't re-answer the question). **No fabrication** — a field the provider omits stays null. Confirmed live 2026-07-23 against the platform Connectively account: `/submitted` returns `{submitted:[{status,publicationSource,domainAuthority,attribution,profileId,featuredQuestionId,...}]}` (statuses: In Review / Selected / Published / Not Selected); `/published` returns `{published:[{publishedLink,articleTitle,publishDate,profileId,featuredQuestionId,...}]}` (172 rows, 100% carry `publishedLink`+`publishDate`, ~95% carry `articleTitle`). **Still NOT exposed by Connectively → tracked in #100:** Domain Rating source-of-truth (DR here is Connectively's own number) and dofollow/nofollow backlink verification via crawling.
  - ⚠️ **Lesson (do NOT re-document a Connectively field as "not exposed / not API-detectable" from probing ONE endpoint).** #101 wrote "Connectively exposes NO published article URL... not API-detectable" into this doc + the reconcile comments after probing only `/submitted` — but the URL/title/date live on the sibling `/published` endpoint (#102 found it, 100% URL coverage on the reported brand). Before declaring a Connectively field unavailable, probe the FULL external-users endpoint surface (`/submitted`, `/published`, `/premium-question-list`, `/opportunities-list`, …) via the platform creds (`key-service /keys/platform/featured-{username,password}/decrypt` → Connectively `/login` → `x-access-token`), not just the one feed already wired.
- `GET /orgs/quote-pitches` also fires a **throttled, best-effort on-read reconcile** (fire-and-forget, ≤ once per `RECONCILE_THROTTLE_MS`=10min per org via `eqrs_sync_state.last_outcome_reconciled_at`) so the report self-populates without an external scheduler — Connectively has no publication webhook, so the report's own poll is the trigger. The explicit POST above is the fail-loud path; the on-read trigger swallows errors (logs). Runs only when EQRS is reachable.
- `POST /webhooks/inbound-email` — HMAC-verified push from email-gateway-service (bronze ingest).
- `POST /internal/process-inbound-emails` — drains pending inbound_emails, runs per-provider parser, writes silver + Gold cluster.
- `GET /orgs/quote-requests`, `/orgs/quote-pitches` — list endpoints for HITL inspection.

## Multi-brand `x-brand-id` CSV

Every `/orgs/opportunities/*` route accepts `x-brand-id: <uuid>` (solo) or `<uuid1>,<uuid2>,...` (co-brand). Server canonicalizes (deduplicates + sorts) into `brand_ids[]`. Solo `[A]`, solo `[B]`, and co-brand `[A,B]` are three independent identity scopes for scoring + pitch idempotency.

| Outbound | Why |
|----------|-----|
| `expert-quotes-requests-service` `GET /orgs/featured/submissions` | **Publication-outcome reconcile** status source (pass-through of Connectively `/submitted`, paginated). JQS decodes it client-side (`fetchSubmittedOutcomes`) and matches onto pitches by `(featured_question_id, featured_profile_id)`. Carries status + outlet + DR + attribution but NOT the article link. Follow-up: EQRS could add a typed, org-scoped outcomes endpoint so JQS isn't coupled to Connectively's raw shape (optimization, not a blocker — JQS only updates its OWN pitches, so cross-org data in the pass-through is inert). |
| `expert-quotes-requests-service` `GET /orgs/featured/published` | **Publication-outcome reconcile** article source (pass-through of Connectively `/published`, paginated; added EQRS-side in #29 / JQS #102). JQS decodes it (`fetchPublishedArticles`) and matches by `(featured_question_id, featured_profile_id)` to persist `featured_article_url` (`publishedLink`), `article_title`, `published_at` (`publishDate`). This is the ONLY Connectively feed exposing the published article URL/title/date. |
| `expert-quotes-requests-service` `GET /orgs/featured/premium-questions` + `POST /orgs/featured/answers` | Featured.com integration. **MVP ingests premium questions** (submittable feed, carry `featured_question_id`); discovery `GET /orgs/featured/opportunities` is no longer pulled (dormant client method). EQRS owns JWT + rate-limit + bronze raw payload + profile bootstrap. **EQRS also owns the `featured-api-pitch-submit` cost: it declares (provision → authorize → execute → actualize) + credit-gates the submit, since it performs the terminal Featured.com call. JQS does NOT declare or gate that cost — it surfaces EQRS's outcome (incl. 402 insufficient-credit) verbatim.** JQS pulls + submits via HTTP. **`mediaOutlet` on premium questions is EQRS-derived (v0.1.10): Featured's `/premium-question-list` has NO outlet field — EQRS derives it from `sourceUrl` hostname (bare host, lowercased; e.g. `dice.com`), `null` only when no source. JQS maps `q.mediaOutlet` verbatim — outlet looks like a bare domain by design. DIS-113.** |
| `chat-service` `POST /complete` | LLM relevance judge (google/flash). One call per `/next` **or** `/discover` tick → 0-100 score + reasoning. Cost is NOT credit-gated by JQS (the consuming workflow owns the budget); each tick is bounded to ≤10 docs. |
| `brand-service` `POST /orgs/brands/extract-fields` | Brand-set profile (industry/expertise/audience/topics) for the judge prompt. Cached 30d brand-side. **Org-route: JQS must forward the full identity trio `x-org-id` + `x-user-id` + `x-run-id` (see invariant below).** |
| `brand-service` | Brand metadata (HARO email signature). |
| `email-gateway-service` `POST /orgs/send` | Outbound dispatch for `email_reply` delivery method. |
| `runs-service` | Run tracking (`withRunTracking` middleware). |

Featured.com is no longer a direct JQS dependency — EQRS owns it.

**Identity-trio invariant (outbound org-routes).** Any JQS→sibling call to an `/orgs/*` route hard-requires the full identity trio `x-org-id` + `x-user-id` + `x-run-id` and validates them **in order** (a missing header 400s on the first one it checks, masking the rest). Forward all three at once — `x-org-id` from `req.orgId`, `x-user-id` from `requireOpportunityIdentity`, `x-run-id` from `req.runId` (`withRunTracking`). `brand-client.extractBrandContext` + `judge-client.judgeRelevance` both do this. Fixing only the header the error names produces a multi-pass prod fix (incident v0.12.1→v0.12.2: added `x-user-id`, redeployed, then hit `x-run-id`). `x-campaign-id` is NOT part of the trio — brand-service uses it only for cache scoping, never 400s on it.

## Ship flow

**No `release.sh`, no `staging` branch.** This service ships straight from `main` — a deploy cron on the host runs `./deploy.sh --all` every 5 minutes off `main`, health-checked with automatic rollback (there is no Railway any more; the whole fleet moved to a single host). Hotfix AND feature both: branch off `origin/main` → `gh pr create --base main` → `gh pr merge <N> --squash` (no `release.sh hotfix`, no staging promote). No required CI checks gate the merge (`gh pr checks` reports none) — `tsc --noEmit` + `pnpm test` locally are the gate.

**Contract verification = PROD registry, not staging.** Because JQS is main-only (no staging deploy), it is ABSENT from `mcp__api-registry-staging__*` (registry name there = a DIFFERENT `journalists`-service). Verify deployed OpenAPI via the **prod** `mcp__api-registry__*` under service name **`journalists-quotes`**. A brief that says "verify on api-registry-staging" is wrong for this repo. ## Tests

- `pnpm test` runs unit + integration. Integration tests need a local Postgres reachable at `JOURNALISTS_QUOTES_SERVICE_DATABASE_URL` (DB schema applied via `pnpm drizzle-kit migrate` — see `tests/setup.ts` for the default URL).
- `tests/setup.ts` hardcodes env defaults (`SCORE_THRESHOLD`, alias routing, etc.) that OVERRIDE the route-level `process.env.X ?? "default"`. **When you change a route's env default, update `tests/setup.ts` too** — otherwise eligibility/threshold tests fail against the stale test value (cost a cycle when `SCORE_THRESHOLD` moved 0.5→30, then 30→10).
- EQRS HTTP client mock lives in `tests/helpers/mock-eqrs.ts` (`buildMockEqrsClient` + `makeOpportunity` + `makePremiumQuestion`; tracks `fetchCalls` + `premiumFetchCalls` + `fetchSinceLog` + `submitCalls`). `/next` ingest uses premium questions (`state.premiumQuestions`); discovery `state.opportunities` is dormant.
- Integration tests `vi.mock` `judge-client.js` (`judgeRelevance` → high/mid/low keyword scorer 85/50/15) + `brand-client.js` (`extractBrandContext` → stub text) to avoid live chat-service / brand-service calls.
- **Tie-break flake**: equal-score opportunities tie-break on `first_seen_at ASC`, but Gold clusters created in ONE ingest batch share an identical `first_seen_at` (transaction `now()`) → tie order is non-deterministic. In `/next` tests where a specific winner is asserted after blocking the top one, give candidates **distinct** judge scores (different `high`/`mid` keywords) so the post-block winner is deterministic. Cost a flaky CI cycle on v0.11.1.

## Future evolution

- If multiple replicas: per-org TTL state moves to DB.
- If the judge `/complete` call becomes a bottleneck under bursty /next traffic: per-org concurrency cap on `pickNextOpportunity` (one in-flight call per (orgId, brandIds) at a time).
- Served-status source of truth → EQRS (per global "collective scoring, atomic exclusion"). W1 uses local `quote_pitches` block; swap to an EQRS submitted-status query once EQRS ships the endpoint (DIS follow-up).
- If Featured publishes a cursor or `since=` parameter, replace `onConflictDoNothing` idempotency with explicit Featured-cursor state (saves O(catalog) work per tick).
